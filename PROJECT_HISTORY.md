# Project history

A running log of what's been built and decided for the berlinbeat.org rebuild, and why — most of this reasoning would otherwise only exist in chat history, not in the code or a commit message.

## Origin

berlinbeat.org is a WordPress.com music journalism site (Berlin scene: interviews, album/show reviews, concert photo galleries), being rebuilt from scratch in Astro — static, self-owned, no more WordPress.

## Stack & content model

- Astro (static output) + TypeScript + Tailwind CSS v4
- Single `posts` content collection (not separate collections per type) — schema in `src/content.config.ts`. Fields: `type` (`interview` | `review` | `photos`), `reviewType` (`album` | `show`, reviews only), `band`, `album`, `venue`, `tags`, `coverImage`, `gallery`, `excerpt`, `draft`
- Tags are derived from post frontmatter at build time, not a separate collection. There is no venues taxonomy anymore (see Design iteration #7) — `venue` is still a real field, just not browsable as its own section.
- Routes: `/` (random rotation, see below), `/interviews/`, `/reviews/`, `/photos/` (all paginated), `/tags/` (index), `/tags/[tag]/`, `/posts/[slug]/`, `/about/`, `/contact/`, `/privacy-policy/`, `/rss.xml`. No `/venues/*` and no `/links/` — both removed, see "Content & navigation cleanup" below.

## WordPress migration

`scripts/migrate-wp.mjs` converts a WXR export into `src/content/posts/*.md`. Run: `node scripts/migrate-wp.mjs scripts/wp-export.xml` (that file is gitignored).

The real export (629 posts, 6MB) was migrated on 2026-08-01. Before running it for real, the export was analyzed directly (category taxonomy, title patterns, image hosts) and the script was iterated against a dry-run scratch copy until output was clean — several real bugs were caught this way rather than after the fact:

- **Paragraph structure was silently broken.** WordPress.com stores post bodies as plain text with blank lines between paragraphs — the `<p>` markup only gets added at *render* time by `wpautop`. Without accounting for that, every article collapsed into one run-on paragraph when converted to Markdown. Fixed with a small `wpautop`-equivalent pass before HTML→Markdown conversion.
- **Title-prefix bugs.** "Show Review: ", "Album Review: ", "Photos: " prefixes were leaking into extracted `band`/`venue` values (e.g. `band: "Photos: Sebadoh"` instead of `Sebadoh`). These prefixes are also stripped from the stored title now, since the UI already shows the type as a separate label.
- **~40% of the site's ~6,000 images are permanently dead.** Early-era posts (~2011-2012) embedded photos from Picasa Web Albums, which Google shut down — those URLs now redirect to a login wall (verified directly). Later posts used Flickr's CDN, which still works, plus some self-hosted `berlinbeat.org/wp-content/uploads/...` images, which also still work. 113 migrated posts are tagged `broken-images` with a TODO comment in their frontmatter so they're easy to find later.
- **23 posts tagged `needs-review`** — mostly multi-band festival photo posts ("Feel Festival Day 1") that don't fit the "Band at Venue" title-parsing pattern, plus a couple of miscellaneous ones.
- **Venue name collisions.** Venue names come from free-text title parsing, so the same venue shows up with different capitalization/punctuation (e.g. `"About Blank"` vs `"://about blank"`) — both slugify to the same URL, which crashed the Astro build with a route conflict. Fixed by grouping venues by slug (`uniqueVenues()` in `src/lib/posts.ts`) and picking the most common spelling as canonical, rather than deduping by exact string.
- **Remote image handling had to change architecturally.** Astro's `<Image>` component fetches every remote image over the network *at build time* just to read its dimensions — with ~40% of images confirmed dead, this crashed the entire site build on the first bad link. Fixed by rendering remote images as plain `<img>` tags (`src/components/SmartImage.astro`) instead of routing them through Astro's optimization pipeline. Every place that's used already constrains images to a fixed-aspect-ratio container, so intrinsic size doesn't matter for layout.

Migration result: 629 posts (263 interviews, 46 reviews, 320 photo posts, 11 kept as WordPress drafts).

**Still open:** the 113 `broken-images` posts need manual photo replacement or removal; the 23 `needs-review` posts need manual reclassification/cleanup.

**2026-08-01, follow-up fix — author attribution was missing.** The original migration script never read `<dc:creator>` from the export, so every post lost its byline. Fixed: `content.config.ts` gained an optional `author` field, the script now builds a login → display-name map from the `<wp:author>` blocks in the WXR header and resolves each post's author (falling back to the raw login if no display name was set in WordPress), and the byline now shows on the post detail page and in the RSS feed. Content was regenerated from the export to backfill this — safe to do since nothing in `src/content/posts/` had been hand-edited yet. If that stops being true (manual QA on `needs-review`/`broken-images` posts has started), re-running the full migration will silently skip every file that already exists rather than overwrite hand-edits — a full regenerate at that point would need those edits preserved or reapplied first.

## Design iteration

The visual design went through several rounds — each one is here so the same ground doesn't get re-covered by mistake:

1. **First pass:** bold editorial look — Space Grotesk display font, large type scale, acid-green accent, dark mode default. **Rejected**: "too big and bold, not minimal/clean."
2. **Toned down:** smaller type scale, single typeface (dropped Space Grotesk), muted accent usage. **Rejected**: "don't like the colors."
3. **Went fully monochrome:** black/white/gray only, no accent hue anywhere — emphasis via underline/weight instead of color. Also stripped decorative shapes (circles/rectangles) from placeholder demo images and switched from a loaded Inter webfont to the OS's native system font stack. **Rejected as a structural direction later**, but the monochrome palette and system font itself were never specifically called out again — likely still the right call, revisit only if told otherwise.
4. **Tightened spacing:** reduced line-height, letter-spacing, and padding/margins sitewide. Applied within the still-current monochrome/system-font base.
5. **Text-forward index list:** dropped all imagery from listing pages, grouped posts by month with thin dividers (offered as one of several explicit mockup options, this one was chosen). **Rejected**: "too lowkey and text forward."
6. **Compact image cards + dropdown filter:** dense card grid (`PostCard.astro` + `PostGrid.astro`), plus a `Show: All / Interviews / Reviews / Photos` dropdown that filters client-side with no page reload (`PostBrowser.astro` — wraps `PostGrid` with the dropdown). Originally used on the homepage too.
7. **Homepage dropdown removed, venues page removed entirely.** Pointed out that with Interviews/Reviews/Photos already in the nav, the homepage's own type dropdown was pure duplication — clicking "Interviews" in nav does exactly what selecting "Interviews" from the dropdown did. Homepage now just shows the 12 most recent posts via plain `PostGrid`, no filter control. `PostBrowser` (the dropdown) is still used on tag pages (`/tags/[tag]/`), where it isn't redundant — nav has no way to filter a single tag's posts by type. The `/venues/` index and `/venues/[venue]/` pages were removed outright (not just the dropdown) — `uniqueVenues()` in `src/lib/posts.ts` went with them since nothing else used it. `venue` remains a real frontmatter field (still shown embedded in post titles, e.g. "Band at Venue Date") — only the dedicated browsing-by-venue UI is gone, not the data.

**Takeaway for future design changes:** vague feedback ("meh", "still don't like it") burned multiple rounds before landing on something workable. Presenting 3-4 concrete options (with ASCII/text mockups where possible) and asking which is closest got a decisive answer in one round every time it was tried. Prefer that over guessing again.

## Infrastructure notes

- This machine uses `asdf` for Node version management; the **global** `~/.tool-versions` pins Node 21.6.1, which Astro doesn't support. Fixed with a **project-local** `.tool-versions` pinning Node 22.17.0 (scoped to this repo only, doesn't touch the global default).
- Port 4321 (Astro's default dev port) is usually occupied by an unrelated project on this machine (`~/Desktop/coastlines`) — the berlinbeat dev server falls back to 4322. Check the terminal's own `npm run dev` output for the actual bound port rather than assuming 4321.
- Astro's dev-mode image endpoint (`/_image?...`) sends `cache-control: public, max-age=31536000` (one year) with no content-hash in the URL — editing a source image and reloading the browser normally will *not* pick up the change. Hard refresh (Cmd+Shift+R) or an incognito window is required to see image edits during development.

## Bugs found post-migration

**2026-08-01 — article body text and links were unreadable (dark-on-dark).** `@tailwindcss/typography` defines its own `--tw-prose-*` defaults (a dark gray palette meant for light backgrounds) inside Tailwind's `utilities` cascade layer. Our own color override for those same variables (`src/styles/global.css`) was written inside `@layer base` — same selector, same specificity, but a **lower-priority layer**. CSS Cascade Layers resolve by layer order first, specificity second, so `utilities` silently won regardless of the fact that `base` came later in file order. The result: all prose/article body text and links rendered in Tailwind Typography's dark-gray-on-light default palette, which on this site's near-black dark-mode background read as dark text on a dark background.

Fix: moved the `.prose` overrides out of `@layer base` entirely, making them unlayered rules — unlayered CSS always wins over any `@layer`-wrapped rule regardless of order, per spec. Verified by inspecting the compiled CSS directly rather than trusting a visual check, since a browser wasn't available this session.

**Lesson for future style changes:** when overriding a Tailwind plugin's own default utility classes (not just Tailwind's core utilities), check whether the plugin's rule lives inside a cascade layer before assuming `@layer base` is enough to override it — it usually isn't.

**2026-08-01 — images looked fuzzy.** Migrated content links to a decade of hotlinked images at whatever size the original WordPress theme requested at the time — mostly the old "medium" thumbnail (`?w=300` on self-hosted `wp-content/uploads` URLs) and Flickr's default ~500px rendition (no size suffix in the filename). Displayed at today's card/cover sizes, both get visibly upscaled by the browser. Confirmed via direct fetch: ~90% of self-hosted image refs (297/328) carry `?w=300`, and the large majority of Flickr refs (3101) have no size suffix at all.

Fix: `src/lib/imageQuality.ts` rewrites remote image URLs to request a larger rendition before they're rendered — `?w=` bumped to 1200 for self-hosted WP uploads, Flickr filenames upgraded to the `_b` (~1024px) suffix unless already at `_c`/`_b`/`_h`/`_k`/`_o`. Verified live before applying broadly (not just assumed): both WordPress.com's Photon-style resizing and Flickr's CDN clamp to the image's actual source resolution rather than upscaling or 404ing on a too-large request, so this can only improve or no-op, never break an image that currently works. Wired into `SmartImage.astro` (covers every card/cover image), `GalleryGrid.astro`'s full-size lightbox link, and the Open Graph image meta tag — all three are the only places a remote image URL gets used directly.

Some images (e.g. a 2011 album cover whose original upload was only 350×350) genuinely can't get any sharper than they already are — the source just doesn't have more pixels. That's a real ceiling, not a bug.

**2026-08-01 — ampersands showed up as literal `&amp;` on the page.** WordPress's own exporter double-escaped some plain-text fields: the raw WXR has `<title><![CDATA[Boy &amp; Bear]]></title>` — the literal text `&amp;` sitting inside the CDATA block, instead of a raw `&`. That's technically valid XML (CDATA content isn't entity-processed, so the parser correctly returns the string exactly as stored, `&amp;` and all), but it meant our migrated `title`/`band`/tag values contained a literal `&amp;` substring rather than `&`. Astro then HTML-escaped that string when rendering — turning the already-literal `&` inside `&amp;` into `&amp;amp;` — which a browser decodes one level to display the visible text `&amp;` instead of `&`.

Fix: `decodeHtmlEntities()` in `scripts/migrate-wp.mjs`, applied specifically to plain-text fields extracted via `textOf()` — title, category/tag names, `dc:creator`, `wp:author_display_name`, and the post-strip excerpt. **Deliberately not applied to `content:encoded`** (the actual article HTML) — that field is real HTML fed to turndown's own HTML parser, which already decodes entities correctly as part of normal parsing; blindly decoding `&lt;`/`&gt;` in raw HTML *before* it's parsed risks turning literal escaped text into what looks like a stray tag. Content was regenerated from the export to backfill this fix across all 629 posts.

## Static-page content

The About and Contact pages were originally built with placeholder copy (never asked for — should have used the real site's content from the start). Both were later corrected to the verbatim original text from berlinbeat.org, plus a new Privacy Policy page:

- **`/about/`**: real mission statement (past-tensed, "(2011–2020)" folded in per instruction) and all 5 contributor bios, restored **exactly as originally written** — not paraphrased. Getting this right took two attempts: the first pass used `WebFetch` (which runs fetched content through a summarization model), and two separate fetches of the *same* page produced two *meaningfully different* paraphrased versions of the same bios — not just reworded, actually different facts included/omitted. That's a reliability red flag, not a rendering-order quirk. Re-fetched via direct `curl` + manual HTML parsing instead (no AI paraphrasing step) and got the complete, verbatim original, including inline links the summarized versions had dropped entirely (e.g. Natalye's bio links her personal site, a book PDF, and the publisher — separately) and the "See all posts by [name] here" author-archive links each bio originally had. **Lesson: for any "reproduce this text verbatim" request, don't trust `WebFetch`'s summarization pass — fetch the raw HTML directly (`curl`) and extract programmatically.** The archive links point to the old berlinbeat.org author pages (`/author/<login>/`) rather than an equivalent on this site, because our migrated `author` frontmatter field doesn't cleanly map to these bio names (e.g. "Lauren"'s posts are stored under `punkrockdoll`, the raw WP login, since no display name was ever set for that account) — building a working internal replacement would mean guessing at fragile name mappings, so it wasn't done silently.
- **`/contact/`**: real contact copy, restored verbatim via the same direct-fetch method from the start (no paraphrasing detour this time).
- **`/privacy-policy/`** (new): the site's actual GDPR privacy policy, reproduced in full (~5,300 words, standard Automattic/DGD-generator boilerplate) rather than retyped by hand — extracted via direct fetch and assembled into the page programmatically to avoid any transcription drift across that much legal text. Linked from the footer.
- Small follow-up edits, each straightforward: copyright year in the `/contact/` copyright notice bumped from the original site's stale "2011-2014" to "2011-2026"; footer tagline trimmed from "© {year} Berlin Beat — Berlin music, up close." down to just "© {year} Berlin Beat"; added visual spacing between each contributor's bio and their "See all posts by..." line on `/about/`.

## Content & navigation cleanup

- **`/links/` removed entirely.** Was a placeholder page (fake example links, never real content) that was never asked for in the first place — removed rather than filled in with real content, unlike About/Contact/Privacy Policy which got the real treatment.
- **Subtitle description text removed from four listing pages** (`/tags/`, `/reviews/`, `/photos/`, `/interviews/`) — e.g. "Conversations with bands and artists passing through Berlin." under the `/interviews/` heading. Removed only the *visible* `<p>` on the page; the same string is still passed through to `<meta name="description">` for SEO, since that wasn't what was asked to be removed.
- **`/tags/` index page added** (didn't exist before — only individual `/tags/[tag]/` pages did). Modeled loosely on how nutrient.io/blog splits browsing into a category dropdown (already had the equivalent via `PostBrowser`) plus a separate "Browse tags" page (this). Of the 638 raw WP `post_tag` values, 412 are one-off band names used on exactly one post each — included them all rather than filtering them out (an earlier version of this page filtered singletons; explicitly asked to add them back), sized by frequency via a simple tag-cloud text-size scale so the page stays scannable despite the volume.
- **Tags moved out of the primary nav into the footer**, next to About/Contact/RSS/Privacy Policy — it doesn't need equal billing with Interviews/Reviews/Photos, and that's roughly where Nutrient's own "Browse tags" link sits too (not their top nav).

## Homepage: random rotation instead of "latest posts"

The site stopped being updated in 2020, so a "latest posts" homepage always shows the same handful from 2020 and implies activity that isn't happening — pointed out directly, agreed it was the wrong framing. Replaced with: a random pool of 120 posts picked at build time (refreshes every deploy), all rendered server-side but hidden, then a client-side script randomly reveals 12 of them on every page load — so it changes on every *visit*, not just every deploy (`src/pages/index.astro`).

Two real bugs surfaced building this, both worth remembering:

1. **Astro's scoped `<style>` silently no-ops on child-component markup.** The hiding rule (`#post-pool > [data-type] { display: none; }`) was written as a normal scoped `<style>` block. Astro scopes styles by rewriting the selector to require a `data-astro-cid-*` attribute — but it only stamps that attribute onto elements written directly in *this* component's own template. The `[data-type]` elements are `PostCard`'s root `<a>`, rendered by a child component, so they never get the parent's scope id. The compiled selector required an attribute that could never be present, so it silently matched nothing — no error, just a CSS rule that does nothing. Fixed with `<style is:global>`. **Always check the actual compiled selector when scoped styles need to reach into a child component's markup — it fails silently, not loudly.**
2. **`element.style.removeProperty('display')` doesn't undo a stylesheet rule.** The reveal script's first version tried to un-hide chosen cards by removing the inline `display` property — but the cards never had an *inline* `display` set in the first place (they were hidden by an external stylesheet rule). Removing a property that isn't there is a no-op; the stylesheet's `display: none` keeps winning. Fixed by adding a `.is-visible` class with `display: flex` at higher specificity, and having the script add that class instead. Caught by tracing the logic by hand rather than assuming it worked — worth being deliberately suspicious of "remove an inline style to reveal something" as a pattern whenever the hiding happened via a stylesheet, not inline styles.

## Photo posts: slideshow instead of a click-to-open-in-new-tab grid

`GalleryGrid.astro` (a grid of thumbnails, each linking out to the raw image URL in a new tab) replaced by `PhotoSlideshow.astro` — one large image at a time, prev/next buttons, click-image-to-advance, arrow-key navigation, a position counter, and a small "Open full size ↗" link that follows whichever slide is active (so the "view the original file" capability the grid had isn't lost, just de-emphasized). Applied the `is:global` lesson from the homepage rotation work immediately this time rather than re-discovering it. Also dropped the separate cover-image block for photo-type posts specifically — it was showing the exact same photo as slide 1 of the slideshow directly above it, once cropped (`object-cover`) and once not (`object-contain`), which read as a mistake once the slideshow existed.

**2026-08-01 — caption text was glued to the next paragraph with zero space, e.g. "...Shotgun JimmieAlthough life on the road...".** Traced to the raw WXR itself, not something the migration introduced: real WordPress's `[caption]...[/caption]` shortcode is a protected block-level unit — `wpautop()` extracts and re-inserts it *before* paragraph-wrapping the surrounding text, which is why the live site rendered it fine even with zero whitespace between `[/caption]` and the next word in the raw source. Our simplified `wpAutop()` reimplementation (see the "images looked fuzzy" entry above for why that function exists at all) has no such special-casing, so stripping just the `[caption]`/`[/caption]` bracket tokens left the trailing caption text (often sitting *inside* the shortcode, after the `<img>`, rather than in a `caption="..."` attribute) directly abutting whatever paragraph came next.

Fix: `stripWpArtifacts()` in `scripts/migrate-wp.mjs` now replaces `[caption...]` and `[/caption]` with blank lines instead of empty strings, so the later `wpAutop()` pass sees a genuine paragraph boundary at each shortcode edge regardless of what the raw source had. Affected 87 posts; verified all 87 got a real fix (not just the one reported) by scanning every migrated post for the glued-text pattern before regenerating content — one false-positive flagged by that scan turned out to be a band literally named "BoySetsFire," not a bug.
